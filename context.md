# Контекст разработки бота (buh_bot)

В этом документе зафиксированы все ключевые изменения, багфиксы и архитектурные решения, реализованные в рамках нашего бэклога на данный момент.

## Задача 1: Критичный баг многопользовательского режима (Блокировка входа)
**Проблема:** Бот был жестко привязан к одному пользователю. Декоратор `@owner_only` стоял перед всеми основными функциями (`start`, `balance`, `goals`, `debts` и т.д.), что не позволяло другим людям использовать бота даже после добавления их в базу через `add_user`.
**Решение:**
1. Мы удалили декоратор `@owner_only` со всех базовых команд в `bot.py`.
2. В функции `start` исправили логику создания профиля — теперь метод `db.get_profile(tg_id)` корректно проверяет наличие пользователя в БД по `tg_id` (паспорту), и только зарегистрированные администратором пользователи получают доступ.
3. Доступ администратора (для команды `/add_user`) был оставлен под защитой.

## Задача 2: Устранение Race Condition (Состояние гонки)
**Проблема:** Ранее бот вычислял новую сумму для целей и долгов на стороне сервера (Python). Логика была такой: `прочитать баланс из БД -> прибавить сумму -> записать в БД`. При одновременных запросах (например, два быстрых вклада по 100 рублей) оба процесса могли прочитать старый баланс "0" и записать "100", тем самым потеряв одну из транзакций (итог был 100 вместо 200).
**Решение:**
Мы перенесли математику на уровень базы данных Supabase, используя атомарные операции через RPC (Remote Procedure Call):
1. **Supabase RPC:** Созданы 3 функции в базе данных:
   - `rpc_add_to_goal(p_goal_id, p_amount)`
   - `rpc_reduce_debt(p_debt_id, p_amount)`
   - `rpc_restore_debt(p_debt_id, p_amount)`
2. **database.py:** Полностью переписаны методы `add_to_goal`, `reduce_debt`, `restore_debt`. Теперь вместо чтения и обновления (UPDATE) они вызывают RPC (`db.rpc(...)`), гарантируя, что прибавление и вычитание происходят атомарно в транзакциях PostgreSQL. Состояние гонки полностью устранено.

## Задача 3: Перенос Черновиков (FSM) из оперативной памяти в Supabase
**Проблема:** Состояние незаконченных операций (Черновиков) хранилось в оперативной памяти сервера `context.user_data["draft"]`. Если пользователь ввел сумму "500", а затем бот упал или сервер был перезагружен, бот забывал, что ждет от пользователя ввода категории для этой суммы.
**Решение:**
1. **База данных:** Спроектирована и создана таблица `user_drafts` со структурой:
   - `user_tg_id` (BIGINT, PRIMARY KEY)
   - `type` (TEXT)
   - `amount` (NUMERIC)
   - `category` (TEXT)
   - `description` (TEXT)
   - `awaiting` (TEXT) - какое поле ожидается следующим
   - `card_chat_id` / `card_message_id` (BIGINT) - для редактирования Inilne-карточки.
2. **database.py:** Добавлены методы `get_draft(tg_id)`, `save_draft(tg_id, draft)` (выполняет Upsert), `clear_draft(tg_id)`. Обновлена функция полного сброса `hard_reset_all`, чтобы она захватывала и `user_drafts`.
3. **bot.py:** Логика кнопок и карточек полностью переписана. Все использования `context.user_data["draft"]` заменены на вызовы методов БД. Во все связанные функции (`_send_draft_card`, `_refresh_draft_card`, `_apply_draft_field`, `_on_draft_button`) добавлен аргумент `tg_id`. 
**Итог:** Бот переживает перезагрузку. Если сервер упал посреди создания черновика, после перезапуска бот подхватит контекст из базы.

## Прочие багфиксы
- **TypeError в _handle_actions:** При отмене операции через ИИ (если распознан экшен `"cancel"`), бот падал с ошибкой из-за отсутствия `tg_id` в функции `_handle_actions`. Аргумент добавлен в четырех местах вызова.
- **TypeError в find_goal_by_title:** "Страховка К8" (когда ИИ распознает 1 расход и бот проверяет, не является ли он закрытием цели) падала, так как при поиске цели по названию отсутствовал `tg_id`. Баг устранен добавлением `tg_id` в `db.find_goal_by_title(tg_id, ...)`. Попутно обнаружено интересное поведение непредсказуемости ИИ: на "1500" ИИ выдавал пустой ответ (что вело к Черновику), а на "500" ИИ фиксировал Транзакцию (что вело к падению).

## Задача 4: Юридический шлюз (Legal Gatekeeper)
**Проблема:** По законам РФ необходимо раздельно собирать согласия на Оферту и Обработку ПДн, а также поддерживать версионность этих документов, не давая пользователю работать с ботом до их принятия.
**Решение:**
1. **База данных (`legal_history`):** Создана таблица `legal_history` для хранения ПЭП (простой электронной подписи) с полями `user_tg_id`, `doc_type` ('offer', 'pd_consent'), `version` и `accepted_at`. На таблицу навешен RLS. Написаны методы `get_accepted_legal_docs` и `save_legal_consent` (с логикой upsert для обновления версии). Обратите внимание: функция `hard_reset_all` намеренно **не** удаляет юридические согласия, так как сброс баланса не означает отзыв согласия на обработку ПДн.
2. **Перехват в `bot.py`:** Заведены константы `CURRENT_OFFER_VERSION = "v1.0"` и `CURRENT_PD_VERSION = "v1.0"`. В самое начало обработчиков `process_text` и `handle_voice` внедрена функция `_check_legal_consent`. Если хотя бы одного актуального согласия нет — бот возвращает `return` (отменяя парсинг текста/голоса) и отправляет Inline-карточку блокировки.
3. **Динамический UI:** В `on_button` добавлена обработка `legal_offer` и `legal_pd_consent`. При нажатии на кнопку документ записывается в БД, а карточка перерисовывается (кнопка заменяется на "✅ Принята" с `noop` callback). Когда оба документа приняты — карточка удаляется и бот приветствует пользователя, полностью разблокируя финансовый функционал.

## Задача 5: Технический паспорт для юриста (Подготовка Оферты и Согласия ПДн)
Подготовлен отдельный артефакт с подробным описанием работы системы для юриста:
- **Данные:** Бот собирает ID, имена, юзернеймы, финансовую аналитику (траты, долги с указанием имен третьих лиц) и профильную информацию.
- **Голос:** Используется исключительно для транскрибации (не для идентификации) и мгновенно удаляется после расшифровки.
- **Трансграничная передача:** Данные пользователей передаются по API внешним ИИ-провайдерам: Groq Inc. (США) и DeepSeek (КНР).
- **ПЭП (Простая электронная подпись):** Фиксация факта нажатия кнопки в Телеграм-боте сохраняется в таблицу `legal_history` с меткой времени, что юридически является ПЭП. Отзыв согласия осуществляется по запросу пользователя.

## Задача 6: Запрет на сбор чувствительных данных (Hardening)
**Проблема:** Юрист посоветовал запретить сбор чувствительной информации (здоровье, религия, номера карт), чтобы бизнес не попал под строгие требования защиты данных особой категории.
**Решение:** В системный промпт ИИ в файле `ai_helper.py` жестко вшит запрет. Бот обучен никогда не задавать уточняющих вопросов, если пользователь упоминает здоровье или подобные темы.

## Задача 7: UX Onboarding и First-Touch Experience
**Проблема:** Новым пользователям было непонятно, в какой валюте ведутся расчеты и как начать работу с ботом. Команды можно было выполнять в обход онбординга.
**Решение:**
1. **База данных:** В таблицу `user_profile` добавлено отслеживание шагов (`onboarding_step` = `currency` -> `profile` -> `done`).
2. **Onboarding FSM:** После принятия юр. документов запускается онбординг (выбор валюты из кнопок, затем опциональное заполнение профиля текстом). Во время онбординга голосовые сообщения блокируются (для экономии API). Выбранная валюта подставляется в команду `/balance` вместо жестко зашитых рублей.
3. **Безопасность (Декораторы):** Написан декоратор `@require_onboarding`, который оборачивает все команды бота (`/balance`, `/history`, `/start` и т.д.). Декоратор гарантирует строгий порядок: сначала юр. документы, затем онбординг, и только потом доступ к финансовым функциям.
4. **Контекстные подсказки (Zero-State):** Команды `/goals` и `/debts` дружелюбно подсказывают, что писать боту, если списки пока пусты.
5. **Автоматическое меню:** В `bot.py` добавлен хук `post_init`, который автоматически при старте бота прокидывает команды в кнопку `Menu` Telegram (через `set_my_commands`).

## Задача 8: Изоляция тестового сервера (Maintenance Mode)
**Проблема:** При развертывании тестового сервера (Staging) любой пользователь, нашедший бота в поиске Telegram, мог воспользоваться им и нарушить статистику.
**Решение:** Во все основные роутеры бота (декоратор `require_onboarding`, функции `reset_cmd`, `on_button`, `process_text`, `handle_voice`) внедрен защитный блок `ADMIN_ONLY_MODE`. При включении переменной окружения `ADMIN_ONLY_MODE=True` в `.env`, бот отвечает всем чужим пользователям заглушкой "🛠 Бот находится на техническом обслуживании", пропуская только администратора (`MY_TELEGRAM_ID`).

## Текущий статус
Бэклог закрыт. Бот стабилен, поддерживает нескольких пользователей, устойчив к гонкам транзакций, не теряет черновики при перезапуске сервера, имеет надежный юридический шлюз с версионированием согласий и плавный онбординг.

# Руководство по DevOps: Миграция на Production (Боевой сервер)

## Архитектура
Мы разделяем проект на две среды:
* **Staging (Тест):** Старый сервер + старый Telegram Token + старая база Supabase. Используется для тестирования новых фич.
* **Production (Продакшн):** Новый мощный сервер + новый Telegram Token + новая база Supabase. Используется реальными пользователями.

## Пошаговый план для перехода (для GEM-бота)

### Этап 1: Подготовка баз данных (Supabase)
1. **Создание новой БД:** Создать новый проект в Supabase для Production бота.
2. **Перенос схемы:** Зайти в SQL Editor старого проекта, скопировать скрипт создания всех таблиц (`transactions`, `goals`, `debts`, `chat_history`, `user_profile`, `user_drafts`, `legal_history`) и выполнить его в SQL Editor нового проекта.
3. **Фикс уникальности:** В новой базе убедиться, что в таблице `user_profile` ключ `key` НЕ является уникальным глобально, а уникальной является связка `(user_tg_id, key)`.
4. **Функции (RPC):** Перенести 3 RPC функции (`rpc_add_to_goal`, `rpc_reduce_debt`, `rpc_restore_debt`) в новую базу.

### Этап 2: Создание Git-репозитория
1. **Инициализация:** В папке с проектом (на компьютере или на старом сервере) выполнить `git init`.
2. **.gitignore:** Убедиться, что создан файл `.gitignore`, куда ОБЯЗАТЕЛЬНО внесен файл `.env`, папки `__pycache__` и `venv`.
3. **GitHub/GitLab:** Создать приватный репозиторий, подключить его к локальному проекту и выполнить `git add .`, `git commit` и `git push`.

### Этап 3: Настройка боевого сервера (Production)
1. **Доступ:** Зайти по SSH на новый сервер.
2. **Клонирование:** Установить `git` и выполнить `git clone <ссылка_на_репозиторий>`.
3. **Окружение:** 
   - Установить Python (желательно 3.10+).
   - Создать виртуальное окружение: `python3 -m venv venv`.
   - Активировать его и установить зависимости: `pip install -r requirements.txt`.
4. **Настройка .env (Секреты):**
   - Вручную создать файл `.env` на сервере.
   - Скопировать туда структуру конфига.
   - **Важно:** Вставить *новый* `TELEGRAM_TOKEN`, URL и API KEY от *новой* базы Supabase. API-ключи для DeepSeek/Groq остаются прежними.

### Этап 4: Запуск в фоне (Daemon/Systemd)
Чтобы бот работал всегда и перезапускался при падении:
1. Создать systemd сервис (например: `sudo nano /etc/systemd/system/hommyfin.service`).
2. Указать в нем пути к рабочему каталогу проекта, путь к Python из `venv` и команду запуска `bot.py`.
3. Запустить и добавить в автозагрузку:
   - `sudo systemctl daemon-reload`
   - `sudo systemctl enable hommyfin`
   - `sudo systemctl start hommyfin`

### Жизненный цикл разработки (Дальнейшая работа)
- Все доработки и изменения кода пишутся и тестируются на Staging сервере.
- После успешных тестов делается `git commit` и `git push`.
- На боевом сервере выполняется: `cd /path/to/bot && git pull && sudo systemctl restart hommyfin`.

### Завершенная миграция на Prod (Текущий статус)
- **Инфраструктура:** Успешная миграция БД на Prod (проект `finance-bot-prod`). Развернут слепок схемы из 7 таблиц (`transactions`, `goals`, `debts`, `chat_history`, `user_profile`, `user_drafts`, `legal_history`).
- **Конфигурация:** Установлено, что библиотека `supabase` для Python не поддерживает ключи в новом формате `sb_secret_`. Для авторизации `service_role` обязательно использование Legacy JWT-токена (начинающегося на `ey...`). URL базы данных должен быть указан без суффикса `/rest/v1/`.
- **Статус:** Демон `buhbot.service` успешно запущен на боевом сервере. Подключение к Telegram API и базе данных функционирует без ошибок.
